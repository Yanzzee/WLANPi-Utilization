# Logging Reference

WLANPi Beacon Live uses one logging service for live display logging and live
logging-only operation. Logging state is separate from analyzer state, so a log
can close without resetting capture metrics or graph history.

## Front-panel controls

Each band/channel menu offers four actions:

| Action | Result |
| --- | --- |
| `Display` | Starts live display capture with logging inactive. |
| `Display + Log` | Starts the same display runtime with both log formats active. |
| `Start Logging` | Starts the same live capture/analyzer in logging-only mode with no graph page. |
| `Stop Logging` | Stops the background logging-only session. |

Pressing left from an active display stops that capture session and cleanly
closes any active logs.

Successful logging start/stop notifications include the tuned channel,
frequency, and `/var/log/wlanpi-beacon-live` folder. `Display + Log` shows the
start notification once, before normal display operation, and the stop
notification when exiting left; both overlays restore the existing display
state. If disk pressure stops logging while the display remains active, a
one-time low-disk notification is shown.

The FPMS adapter prevents a separate display capture from starting while a
logging-only capture is already active. Stop the logging-only session first.

## Terminal controls

Choose one or both live formats:

```bash
sudo .venv/bin/wlanpi-beacon-live \
  --iface wlan0 \
  --channel 36 \
  --stats-csv \
  --beacons-jsonl \
  --log-dir logs
```

`--logging-only` disables terminal/LCD rendering and automatically enables both
formats:

```bash
sudo .venv/bin/wlanpi-beacon-live \
  --iface wlan0 \
  --channel 36 \
  --logging-only \
  --log-dir logs
```

Ctrl-C flushes pending analyzer statistics, closes enabled files, terminates
TShark, and exits.

## Locations and filenames

- FPMS logs: `/var/log/wlanpi-beacon-live`
- CLI default: `logs` relative to the current directory
- CLI override: `--log-dir <directory>`

The third FPMS auxiliary button saves the currently displayed screen as a PNG
in the FPMS log directory. Its filename contains local time, the screen name,
and tuned frequency, for example:

```text
20260720-143005-123456_retry-percentage_5180MHz.png
```

This is a copy of the already composed display image. It does not rotate the
active screen or pause capture, analysis, display refresh, or logging. After a
successful save, a brief overlay confirms the destination folder and restores
the same display screen.

Live filenames are generated by the app and include local time plus a UTC
offset:

```text
beacon_live_20260720T120000123456-0600_stats.csv
beacon_live_20260720T120000123456-0600_beacons.jsonl
```

The two formats in one segment share a prefix. The directory is created
recursively. Live format flags do not accept custom filenames.

## Stats CSV

The stats file contains one row for each emitted capture second. Columns cover:

- local timestamp, interface, channel, resolved frequency, and band;
- retained BSSID count, summed latest QBSS station counts, and the unique
  eligible client-MAC count detected during that one-second period;
- selected QBSS utilization and source identity/RSSI;
- received, Retry-bit-readable, retry-eligible, and retry-frame counts;
- retry percentage, selected beacon-rate percentage, and retry footer BSSID;
- strongest-radio beacon received/expected counts and beacon-loss percentage;
- optional local survey utilization.

Rows use local ISO-8601 timestamps with offsets. The logging worker flushes
each row as it writes it.
The client field is named `unique_client_mac_count`. It is a per-second count,
matching the cyan Stations graph sample; it is not the 120-second `MAC` summary
total and does not contain a list of addresses.

## Beacon JSONL

The beacon log contains one JSON object for every valid parsed beacon while
logging is active. Objects contain local time, run metadata, SSID/BSSID, QBSS
values, RSSI, beacon interval, AP-name/vendor clues, and the other normalized
beacon fields available to the parser.

The logging worker flushes each line as it writes it. Normal beacon objects do
not include a `record_type` field; the low-disk marker described below does.

## Capture-path isolation

Beacon and completed-second records are handed to one bounded FIFO logging
queue. A dedicated logging thread serializes and flushes them in capture order,
so normal filesystem latency does not stall TShark stdout draining or analyzer
publication. Stop, rollover, and low-disk transitions drain and join the worker
before files are closed. If the queue fills during a sustained disk slowdown,
the producer waits rather than dropping output.

## Disk-space safety

Every active **live** logging session checks the target filesystem immediately
after opening and then periodically. Defaults are:

- minimum free space: 256 MiB;
- check interval: 30 seconds.

The check is scheduled by the live runtime, not by display refreshes. It is
therefore active with or without an LCD/terminal renderer.

When free space falls below the threshold:

1. the service writes an end-of-log marker to each enabled format;
2. both files are flushed and closed;
3. display mode keeps capturing/analyzing with logging inactive; or
4. logging-only mode terminates capture and exits cleanly.

A disk-usage query failure is handled conservatively like low disk. If the
filesystem becomes completely full between checks, the app still closes the
logging service; the reserved threshold makes successful marker writing much
more likely but no filesystem can guarantee a final write after `ENOSPC`.

### Low-disk markers

The JSONL marker is a structured object with:

```json
{
  "record_type": "end_of_log",
  "reason": "disk_space_nearly_full",
  "message": "END_OF_LOG: logging stopped because free disk space was nearly full"
}
```

The actual object also includes local time, free/threshold byte values, and run
metadata.

The CSV marker preserves the existing CSV header. It writes the same
`END_OF_LOG` message in `selected_qbss_ssid`, retains timestamp/run metadata,
and leaves metric cells blank. Consumers should ignore that row as a metric
sample.

Normal manual shutdown does not add a disk-pressure marker.

## Rollover

Live logging starts a new file segment every 3,600 seconds (one hour) by
default. The current files close before the next pair opens. Later segments use
a timestamped prefix plus a predictable part suffix such as:

```text
beacon_live_20260720T130000000000-0600_part0002_stats.csv
beacon_live_20260720T130000000000-0600_part0002_beacons.jsonl
```

Rollover does not restart capture, the analyzer, or graph history.

## Configurable live limits

```text
--min-free-mb N          stop below N free MiB
--disk-check-seconds N   disk check interval
--rotation-seconds N     rollover interval
```

All values must be nonnegative/positive as appropriate. Run
`wlanpi-beacon-live --help` or `beacon-live live --help` for the current CLI.

## Replay logging

Replay accepts explicit output paths because it processes a bounded saved
input rather than an open-ended live session:

```bash
.venv/bin/beacon-live replay \
  --input samples/tshark_qbss_sample.tsv \
  --stats-csv logs/replay-stats.csv \
  --beacons-jsonl logs/replay-beacons.jsonl
```

Replay preserves the same CSV/JSONL record formats but does not use live file
rollover controls.

## Privacy

Logs can contain real SSIDs, AP BSSIDs, RSSI, channel/frequency details, and AP
name/vendor information. Generated `logs/` content is ignored by the repository
and should be sanitized before sharing or committing.
